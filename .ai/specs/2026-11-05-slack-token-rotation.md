# Slack token renewal

Supports unchanged long-lived app/bot credentials and rotating `xoxe.xapp-` / `xoxe.xoxb-` tokens. The wizard detects token prefixes, reveals only the matching refresh-token fields and shared Client ID/Client Secret, and discards hidden renewal values when switching back to long-lived tokens. No new environment switch, migration, hosted capability, or automatic installation.

Both credentials are checked before the first API call. Each rotating token is exchanged once on setup to establish a known expiration and verify renewal. Subsequent requests and the active socket's 30-second watchdog renew within five minutes of expiry. Idle, disconnected integrations perform no background network work; the next call checks expiry after restart or sleep. Shutdown awaits an outstanding renewal. Ordinary tokens never invoke OAuth or create rotation state.

The original credential envelope and consent fingerprints stay immutable. Renewed access/refresh pairs live in cezar-only encrypted project secrets keyed by a hash of the initial refresh token, kind and OAuth client credentials. This shares renewal across receivers and wires without invalidating grants or delivery revisions. A cross-process filesystem lock uses the existing PID-owner lease helper; lock names contain only hashes, under cezarHomeDir()/slack-token-locks. These are disposable state, not configuration. Use a dedicated app per project as before.

Before exchanging a single-use refresh token, write a pending marker to the encrypted store. After a successful exchange, persist the new pair even when the caller was cancelled, then recheck its authorization fence before making any ordinary Slack request. Read/write errors never expose provider response bodies or credentials. Explicit HTTP 429 restores the prior state for a bounded retry. An ambiguous network response, crash, invalid response, or failed save after the exchange leaves pending state: do not replay that refresh token. Ask the user for fresh credentials. This is a deliberate recovery limit, not a claim of exactly-once delivery across Slack and the local vault.

Repair connection opens the existing receiver's setup with its revision, retaining the receiver and notification settings; the operator confirms the chat and task-control permissions again. Routine renewal never re-pairs or changes grants. No token values appear in API responses, logs or check/agent environments; generic redaction covers app, rotating access and refresh token shapes.

Verification: legacy compatibility, both rotating kinds, mixed kinds, concurrent wires, real encrypted-store restart and audience, expiry, rate limits, interrupted exchange, write failures, cancellation fences, heartbeat renewal/shutdown, hidden-field exclusion, repair UI, and browser setup/restart/task flow on simulated Slack. Official API: https://docs.slack.dev/authentication/using-token-rotation/ and https://docs.slack.dev/authentication/tokens/.
