A local Cezar server can receive answers and confirmed new tasks from a Telegram account approved for task control.
Enable `CEZ_WEBHOOKS=1` and `CEZ_CHAT_INBOUND=1` when starting the server. Notifications
and task control are configured together by the Telegram setup wizard.

> **Good to know**: A paired person can instruct a coding agent that runs shell commands on this machine. Approve only people you trust.

## Where to find it

Settings → **External integrations** → **Connect Telegram**

## Set up task control

Open **Connect Telegram**. When `CEZ_CHAT_INBOUND` or `CEZ_WEBHOOKS` is off, the
panel explains which flag is missing. The guided setup is one flow for notifications,
private chats and groups:

1. Enter or choose the bot and confirm **This bot is dedicated to this project: no
   other application receives its messages.** Polling does not begin before this
   consent and final activation. For a group, also confirm **I understand that all
   group members can read project messages, including people without permission to
   control tasks.**
2. Choose **Open Telegram** and press **Start** in the private chat with the bot.
   This one private **Start** identity proof identifies the person who will receive
   task control.
3. On **Confirm task control**, check the person's name, optionally allow **Cancel
   tasks** and **Continue tasks (may incur costs)** (both off by default), read the
   shell-access and cost warning, and choose **Activate task control**. For a group,
   first compare the **Comparison code** with the code the bot sent that person
   privately and tick **I compared this code with the code the bot sent to this
   person privately.**

Task control is not active until activation succeeds. Leaving the setup (**Cancel
setup**, **Not this person**, **Exit setup**, collapsing the panel) cancels the
pending link, so abandoned attempts never use up pairing slots. The link expires
after five minutes, and restarting Cezar expires it too.

A private chat serves exactly one person, the owner of that chat. To add someone
else, choose **Add a chat** (the button reads **Connect Telegram** until a bot is
connected), paste the same bot token and complete the private **Start** proof for
that person. A group member is approved under **People and permissions** →
**Approve a person**, which appears only while a chat still waits for a person;
the visibility confirmation and comparison code still apply. **People and
permissions** lists every approved person with their permissions.

If the receiver was paired with a different bot, the setup asks first: **Replace
pairing and create link** removes every approved person and reply link for that
receiver; **Keep current access** leaves it unchanged.

The same choice appears after changing the receiver’s chat, including moving to
a different group or changing a private chat after revoking its last person.
Choose the receiver in the setup again and confirm the replacement. Group
visibility consent, the comparison code and membership checks still apply.
For a private receiver whose bot token changed, use the setup again if
**Enable replies** is refused.

Use one bot per project. Another application receiving updates for the same bot
can cause a conflict. The bot token stays in Cezar's project secret store.

## Answer a waiting task

Reply directly to a bot notification, or send `/tasks`, `/status <task-id>` or
`/reply <task-id> <text>`. `/tasks` lists up to ten tasks, waiting tasks first.
When a task asks one question with fixed choices, `/status` and the **Task needs
your input** message of a task started from Telegram show one button per option.
Tapping an option sends its label to the task exactly as a Reply would: the same
checks apply, and a question that changed, was answered in the cockpit or is
older than 15 minutes refuses the tap and delivers nothing. Only the person the
buttons were sent to can use them, once. A question that accepts several options,
or an ask with several questions, has no buttons: Reply to the message with your
answer.
A Reply to a finished task is refused with a hint to resume it in the cockpit or
with `/continue`. A shortened ID must have at least eight characters and
identify exactly one task. Approved access covers all tasks in the project,
including those outside the receiver's notification filter.

An ordinary text message in the same approved private chat stays in the latest
task context until you start or explicitly address another task. While that task
is waiting, the text answers its latest question. After it finishes, the same
text starts the existing Continue flow for that task; if Continue permission is
enabled, the bot shows the normal cost and account preview before doing anything.
Commands such as `/tasks`, `/status` and `/reply` are handled by the bot and never
become task answers. Plain text in a group, or in a private chat with no task
context, receives the normal help response and does not reach a task. An answer
or continuation is an instruction to the coding agent and can start paid work.

## Start a task

In the private chat with the bot, a person with **Task control** sends
`/task <text>`. The bot does not start anything yet: it shows a preview with the
text, the project, the workflow (`quick-task`) and the provider, and a
**Confirm** and a **Cancel** button. Only **Confirm** starts the task. It works
once, for two minutes, for the same person in the same chat; access and provider
availability are checked again at that moment. `/task` without text answers with
a short example. Groups cannot start tasks.

Cezar then sends one acknowledgement, for example **Started task `abcd1234`.**,
then bounded progress/questions and one final message such as **Status:
Completed**. When the task finishes or is ready for review, the final message
also carries the agent's last reply after **Agent:**, so a question such as
"what is the latest commit?" gets its answer in the chat. The same holds when the
agent ends its reply with a question of its own: **Task needs your input**
carries that reply, so you can answer it in the chat. Known secrets and file
paths are removed on a best-effort basis. A reply too long for one Telegram
message is shortened and ends with **The full reply is in the cockpit.** This
goes only to the private chat of the person who started the task and does not
need the excerpt option. The **Repository:** line says what happened to the
code, for example **Unchanged** or **Pull request opened**; it is not the
agent's answer. A final response is not another task execution. If delivery
fails after the task was accepted, inspect the task in the cockpit and do not
send `/task` again blindly.

`/status` without a task ID shows your latest task started from that chat.
`/status` never includes what the agent wrote, so it cannot be used to read
other tasks' output.

For a task started from Telegram, the bot sends these messages itself as soon as
the task changes, without the receiver's notification delay. If two-way replies
are not running (Cezar started without `CEZ_CHAT_INBOUND=1`, Task control off for
the receiver, or the bot stopped), the receiver's ordinary notifications take
over. After such a gap the final message can arrive twice.

Task-control setup displays a shell-access and provider-cost warning. Approve
only people you would allow to run commands in this project. A receiver nobody is
approved for only sends notifications; messages sent to its bot are not read.
A delivery acknowledgement means Cezar accepted the message, not that the agent
completed it. Structured questions show their text. For ordinary assistant prose,
Telegram shows a waiting notice; it carries the end of the agent's message only
when the receiver uses Standard content and has **Include an excerpt of the
agent’s last message** turned on;
otherwise read the text in the cockpit.
Pairing does not change the receiver's notification delay. A Telegram receiver
created while inbound Telegram is available proposes 60 seconds; others keep
their own value (3 minutes by default).

Keep the computer and Cezar running. Commands older than 15 minutes are rejected,
and the bot asks you to send them again;
Telegram retains updates for at most 24 hours. If an interrupted action has an
uncertain outcome, inspect the task before retrying. Cezar does not automatically
repeat it. Simultaneous cockpit and Telegram answers may both reach the agent.

## Groups and task controls

For a group or non-forum supergroup, create a receiver with its negative chat ID.
Run the same guided setup: confirm that all members can read project messages,
including people without control permissions, then each person opens the link in
their private chat with the bot; compare the six-digit code there with the cockpit
and activate. Forum groups are not supported.
In groups, address commands to the bot, for example `/status@my_bot <task-id>`,
or reply directly to a bot notification. The bot's help and hints in a group use
that addressed form, and the approval message names `/tasks@my_bot`. A group grant applies only in that group.
A group migration or removal of the bot suspends reception and requires fresh setup.

**Cancel tasks** and **Continue tasks (may incur costs)** are separate permissions,
disabled initially. `/cancel <task-id>` and `/continue <task-id> [text]` display
a preview with a **Confirm** button. Confirm within two minutes using the same
Telegram account and chat. A button works once; restarting Cezar invalidates it.
Continue shows the saved provider, account and model choice, and warns about cost.
A missing or unavailable recorded account requires attention in the cockpit.
Changing permissions, task state or saved configuration requires a fresh preview.

Per-tool **Allow**/**Deny** buttons for an agent's permission prompts are not part
of the first release; answer those in the cockpit.

## Delivery limits

Replies and notifications using the same verified bot share a sending budget:
at most one message per second to a chat and ten per second across the bot.
Ready chats take turns, so a busy group cannot drain its whole backlog before
another chat gets a turn. Existing project notification limits still apply.

If Telegram asks the bot to wait, both replies and notifications respect that
pause. Notifications remain in the durable queue; short-lived replies can expire.
Confirmation-button acknowledgements use a separate, bounded path and respect
their own Telegram cooldown. Restarting reception does not reset these limits.
Bots without two-way setup retain their existing notification behavior.

## Stop or repair access

**Disable replies** preserves approved people. While replies are off, reception stops;
if this is the last active receiver, an approved person who writes to the bot receives
no notice because the bot is no longer polling. A notice is possible only while another
active receiver keeps that bot polling.
**Revoke access** removes a person. **Reset access** removes all approvals and
reply links, requiring fresh setup. **Disconnect bot** also releases its project
assignment. Re-enabling a group receiver asks again that all members can read
project messages.

Changing a paired bot or chat suspends replies until the unified wizard verifies
the replacement. Start the server with both variables to change access. Turning
either variable off stops reception and keeps stored approvals.

A missing or damaged state never restores approvals automatically. **Reset access**
becomes available only when Cezar can verify the complete state and its bot
assignment. If the state changes while you decide, refresh the status first.

**Diagnostics** (collapsed by default) holds two lists. **Recent Telegram
actions** shows each command with the person's name, the eight-character task ID
and the outcome.

If setup is stuck at **Open Telegram and press Start**, press **Start** in the
private bot chat, use a fresh dedicated bot, and keep the setup page open. If the
link expired, choose **Try again** for a new link rather than reusing an old one. If the bot is
assigned elsewhere or has a webhook/polling conflict, stop that other consumer
before reconnecting. **Reset access** clears approvals and pairing links; it is
available only when Cezar can verify the stored state. A damaged or orphaned
assignment is repaired from **Diagnostics** → **Bot assignments**.

**Bot assignments** can release an assignment belonging to a missing
project, after confirmation. A running owner, a changed assignment or a restored
project blocks release. The list shows when diagnostics are incomplete.
After you disconnect, another app that uses the same bot may need to set up its
own message delivery again.
